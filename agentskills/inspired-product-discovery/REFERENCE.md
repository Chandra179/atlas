# Reference

## Discovery principles

From INSPIRED (Marty Cagan). Treat these as constraints on every discovery cycle.

1. **It's all about risks, not features.** Discovery exists to de-risk value,
   usability, feasibility, and business viability — not to generate ideas.
2. **Work in small batches.** Fast feedback beats big-bang releases. A discovery
   cycle should take days, not weeks.
3. **Test cheap, learn big.** Use the cheapest prototype that can answer the risk.
4. **Be skeptical.** Assume your idea is wrong until evidence says otherwise.
5. **You cannot validate your way to a product.** Customer "I'd use that" is not
   evidence. Test real behavior, not stated preference.
6. **One feature vs. many:** test the whole product concept, not feature by feature.
7. **Iterate, don't waterfall.** Move prototype → test → learn → new prototype.
8. **Design and engineering are first-class in discovery.** Not just PM.
9. **The value test is the killer test.** If users won't choose it, nothing else
   matters. Run it early and often.

## The four risks in detail

| Risk | Core question | How you test it | Prototypes |
|------|--------------|-----------------|------------|
| **Value** | Will users choose to use/buy it? | Concierge, Wizard of Oz, live-data, landing page with real commitment | anything that makes value tangible |
| **Usability** | Can users figure it out? | Usability test on a prototype with real users | wireframe, hi-fi clickable |
| **Feasibility** | Can engineers build it? | Technical spike / high-fidelity prototype with real tech | hi-fi prototype, existing product hack |
| **Business viability** | Will sales/support/legal/revenue/marketing support it? | Internal review with stakeholders; mock pricing & policies | concierge, live-data |

## Prototyping techniques (cheapest-first)

| Technique | What it is | Best for |
|-----------|-----------|----------|
| **Problem interviews** | Talk to users about behavior/past | understanding the problem |
| **Wireframes** | Low-fi layout sketches | usability direction, alignment |
| **Hi-fi clickable prototype** | Interactive, non-coded UI | usability testing, value testing |
| **Live-data prototype** | Real product, real features, but only for a few test users | value testing, feasibility |
| **Concierge** | Manually deliver the service yourself to simulate the product | value testing, viability |
| **Wizard of Oz** | Product looks automated but a human runs the back end | value testing, feasibility |
| **Feasibility prototype** | Hack/prototype using real tech to prove it can be built | feasibility |
| **Landing page with commitment** | A page describing the product; capture signups/real intent | value testing, viability |

## Product discovery technique catalog (Cagan's list)

Customer interviews, Concierge, Wizard of Oz, usability testing, value testing,
feasibility testing, technology spikes, opportunity assessment, landing pages,
A/B testing (delivery, not discovery), live-data prototypes, data/fake-door tests
(careful — only where ethical).

## Good vs. bad product patterns

**Bad patterns to name and counter:**
- **Feature factory**: a team that just ships features with no ownership of outcomes.
- **Roadmap-as-features**: a list of features committing you before you know value.
- **Project-based delivery**: "what" is decided above, team only executes "how".
- **Pharma/waterfall process**: requirements → design → build → test, discovery skipped.
- **Sales-driven roadmap**: build whatever the biggest customer asks for, unvalidated.

**Good patterns to build:**
- Empowered, outcome-owning product team (PM + designer + engineers).
- Product strategy and vision before roadmap; roadmap shows problems, not features.
- Continuous discovery feeding an incremental delivery pipeline.
- Kill-and-learn culture: cheap experiments, fast kills, no blame.

## Empowered product team operating model

- **Product Manager**: discovery lead; owns value risk; deep in customer problems.
- **Product Designer**: owns usability risk; designs prototypes and tests them.
- **Engineers**: own feasibility risk; actively prototype during discovery.
- **Tech Lead**: technical strategy + architecture alongside the team.
- Together they own a **product** (outcome), meet weekly, prototype together, and
  both run discovery *and* deliver what's proven.

## Opportunity assessment signal checklist

- Is it a real, frequent, painful problem (or a big new opportunity)?
- Do users today have a workaround they hate?
- Does it fit our product strategy and principles?
- Can we actually build it (feasibility) and does the business support it?
- Is the payoff (value to users and to the business) worth the effort?
