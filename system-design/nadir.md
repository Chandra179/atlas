# Nadir Architecture

Nadir is a single-node RAG search engine with conversational retrieval.

## System overview

Nadir combines document ingestion, hybrid retrieval, reranking, and
local language-model generation in one application. Vector Qdrant stores the
document chunks, semantic-cache entries, and chat history in collections. 

```text
Documents ──> ingest ──> chunks ──> enrich ──> embeddings ──> Qdrant
                                                               │
User ──> chat ──> rewrite ──> cache ──> hybrid retrieval ──> rerank
                                                               │
                                              prompt ──> generate ──> stream answer
                                                               │
                                                        chat history
```

## Main components

- **Application layer** — exposes the HTTP API and coordinates ingestion,
  retrieval, conversations, and streaming responses.
- **Document index** — stores searchable chunks and their metadata.
- **Chat history** — stores ordered sessions and complete turn snapshots so
  conversations can be continued, replayed, edited, or deleted.
- **Semantic cache** — stores query-level results for near-duplicate
  questions.
- **Model services** — provide embeddings, answer generation, query
  rewriting, and optional enrichment.
- **Reranker** — optionally applies a cross-encoder to the small set of
  candidates returned by retrieval.

The document index, chat history, and semantic cache are separate concerns.
They may share the same database technology, but they have different
lifecycles and are cleared independently.

## Document ingestion flow

1. Discover configured source documents and ignore unchanged files using a
   content hash.
2. Convert supported PDFs to text when document conversion is enabled.
3. Split text using headings and paragraph or sentence boundaries. A bounded
   character split is used only when a section is too large.
4. Optionally enrich each chunk with contextual introductions or hypothetical
   questions generated by a language model.
5. Create deterministic chunk identifiers from the source identity and chunk
   position. This makes re-ingestion an idempotent replacement operation.
6. Embed the final chunk text and replace the source's previous indexed
   chunks.

Enrichment is performed during ingestion rather than during search, so query
latency remains predictable. Changing embedding prefixes, dimensions, or
enrichment behavior requires re-indexing the affected documents.

## Query and answer flow

1. Accept a question and optional conversation/session context.
2. For a follow-up question, optionally rewrite it into a standalone query
   using the recent conversation turns.
3. Check the semantic cache using embedding similarity. A cache hit can skip
   retrieval and reranking.
4. On a cache miss, run two retrieval legs in parallel:
   - dense vector search for semantic similarity;
   - BM25 sparse search for exact words, names, and identifiers.
5. Fuse the ranked lists with Reciprocal Rank Fusion (RRF), which combines
   ranks without requiring dense and sparse scores to share a scale.
6. Apply diversity limits such as a per-source cap so one document cannot
   dominate the result set.
7. Optionally rerank the leading candidates with a cross-encoder.
8. Build a citation-oriented prompt from the selected passages, placing the
   strongest context where it is less likely to be lost in a long prompt.
9. Stream generated tokens to the client. Persist the question, retrieval
   evidence, prompt, answer, timing, and errors as one reviewable turn.

If rewriting, caching, reranking, or generation is disabled, the remaining
pipeline still supports direct retrieval. Optional enrichment and rewriting
are best-effort features; a failure does not make the core search path
unavailable.

## Conversation model

Chat sessions contain an ordered sequence of turns. Editing a previous turn
keeps the same session, removes that turn and every later turn, and executes
the replacement against the retained prefix. This preserves a single
conversation timeline instead of creating hidden branches.

The chat stream uses a bounded, insertion-ordered event log. Subscribers can
replay events after a cursor, and disconnecting a subscriber does not cancel
generation. The current broker is process-local and intended for a single
application instance. Horizontal scaling requires a shared ordered event
backend, such as Redis Streams, plus a clear strategy for routing subscribers
to the process that owns a turn.

## Storage and lifecycle boundaries

- Ingest updates the document index and invalidates affected semantic-cache
  entries.
- A full document reset clears the document index and semantic cache, but not
  chat history.
- Deleting one chat or all chats affects only the chat-history collection.
- Chat-history persistence is independent from the live answer stream, so
  users can receive a response even when persistence is temporarily degraded.

## Deployment direction

The current architecture is recommended for a private, single-node
deployment: it is simple to operate, keeps data local, and avoids premature
distributed coordination. Qdrant and the model services can run beside the
application or as separate services on the same network.

For a larger deployment, the main required change is not splitting every
domain into a service. Keep ingestion, retrieval, and chat boundaries intact,
then introduce shared infrastructure where state is currently process-local:

- a shared ordered event backend for live chat streams;
- shared or replicated model services;
- centralized observability and request correlation;
- explicit ownership and concurrency rules for ingestion and cache
  invalidation.

This keeps the current design maintainable while leaving a practical path to
horizontal scaling.
